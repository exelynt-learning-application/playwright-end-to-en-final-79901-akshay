PROJECT GOAL
Build a maintainable Playwright end-to-end test framework for EXELYNT covering:
1. Learner registration and login.
2. Browsing courses and enrolling in a course.
3. Completing a lesson and viewing learning progress.
4. Taking an assessment and viewing the score.
5. An administrator creating a course draft.

The framework uses:
- Page Object Model (POM).
- Reusable Playwright fixtures.
- Separate learner and admin authentication state.
- Unique test data and cleanup.
- Accessible locators and web-first assertions.
- GitHub Actions continuous integration.
- HTML reports, screenshots, and traces for debugging.

File: playwright.config.js

const { defineConfig, devices } = require('@playwright/test');

module.exports = defineConfig({
  testDir: './tests',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 1 : 0,
  workers: process.env.CI ? 2 : undefined,
  reporter: [
    ['list'],
    ['html', { outputFolder: 'playwright-report', open: 'never' }]
  ],
  use: {
    baseURL: process.env.BASE_URL,
    headless: true,
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure',
    actionTimeout: 15000,
    navigationTimeout: 30000
  },
  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] }
    }
  ]
});

CONFIGURATION EXPLANATION
- testDir keeps all automated tests inside the tests folder.
- fullyParallel allows independent tests to run concurrently. Tests that modify shared data must use separate data or be isolated.
- forbidOnly prevents accidental test.only from reaching CI.
- retries are limited to one in CI for diagnostics. A retry is not considered a fix for flaky tests.
- workers are limited in CI to reduce load on the shared staging environment.
- list reporter gives readable terminal output.
- HTML reporter provides a detailed report.
- trace, screenshot, and video help diagnose failures.
- baseURL is read from the environment so the test suite can run against an approved test environment.

Before execution, set BASE_URL to the real EXELYNT staging URL. Never silently run destructive tests against production.

class LoginPage {
  constructor(page) {
    this.page = page;
    this.email = page.getByLabel('Email');
    this.password = page.getByLabel('Password');
    this.submitButton = page.getByRole('button', { name: /log in|sign in/i });
  }

  async open() {
    await this.page.goto('/login');
  }

  async login(email, password) {
    await this.email.fill(email);
    await this.password.fill(password);
    await this.submitButton.click();
  }
}

module.exports = { LoginPage };

File: pages/CourseCatalogPage.js

class CourseCatalogPage {
  constructor(page) {
    this.page = page;
    this.search = page.getByRole('searchbox');
  }

  async open() {
    await this.page.goto('/courses');
  }

  async searchCourse(courseName) {
    await this.search.fill(courseName);
  }

  courseCard(courseName) {
    return this.page.getByRole('article').filter({ hasText: courseName });
  }

  async openCourse(courseName) {
    await this.courseCard(courseName).getByRole('link').click();
  }
}

module.exports = { CourseCatalogPage };

PART 9 - LOCATOR, ASSERTION, AND RELIABILITY RULES
============================================================

LOCATOR RULES
Prefer:
- getByRole()
- getByLabel()
- getByPlaceholder()
- getByTestId() only when needed
- Scoped locators for repeated course cards and buttons

Avoid:
- Long CSS selectors.
- Fragile XPath expressions.
- Selectors based on element position.
- Locators that depend on changing visual layout.
- Selecting the first matching button when multiple buttons exist.

ASSERTION RULES
Use Playwright web-first assertions:
- expect(locator).toBeVisible()
- expect(locator).toHaveText()
- expect(locator).toBeEnabled()
- expect(page).toHaveURL()

Do not use fixed sleeps to wait for ordinary UI updates. Wait for the expected element, state, or network response.

RELIABILITY RULES
- Make each test independent.
- Do not depend on execution order.
- Use controlled test data.
- Keep retries limited.
- Investigate failures rather than hiding them with retries.
- Save traces and screenshots for failed tests.
- Run the complete suite five consecutive times before claiming five-run reliability.

PART 13 - FIVE-MINUTE WALKTHROUGH SCRIPT
============================================================

MINUTE 1 - INTRODUCTION AND STRUCTURE
This is the EXELYNT Playwright automation framework. It covers learner registration and login, course browsing and enrollment, lesson completion and progress, assessment scoring, and admin course draft creation. The tests folder contains scenarios, pages contains page objects, fixtures contains shared setup, utils contains helpers, and data contains controlled test data.

MINUTE 2 - PAGE OBJECTS AND LOCATORS
The framework uses Page Object Model to separate page locators and reusable actions from test intent. It prefers accessible roles and labels. Tests use web-first assertions to verify meaningful user outcomes rather than simply checking that a page opened.

MINUTE 3 - AUTHENTICATION AND ISOLATION
Learner and admin authentication are separate. Storage state can reduce repeated login setup for tests that are not specifically testing authentication. Registration and login retain dedicated end-to-end tests. Unique data and cleanup prevent one test from affecting another.

MINUTE 4 - CI AND RELIABILITY
GitHub Actions installs dependencies and browsers, runs the suite, and saves reports and failure artifacts. Traces and screenshots help diagnose failures. Retries are diagnostic only; they are not a substitute for fixing flaky tests. The suite must be verified over five consecutive CI runs.

MINUTE 5 - DESIGN DECISION AND NEXT STEP
If I started again, I would establish test-data isolation and API-based setup earlier because shared accounts and records can cause flaky tests. My next step is to expand role and permission coverage, add accessibility checks to important pages, and add a performance smoke check with a realistic threshold.
